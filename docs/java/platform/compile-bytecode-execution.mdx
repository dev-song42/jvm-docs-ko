## 학습 목표

- `.java` 파일을 컴파일한 결과와 프로그램을 실행한 결과를 구분합니다.
- 소스를 수정한 뒤 다시 컴파일해야 하는 이유를 파일의 변화로 설명합니다.
- 오류가 컴파일 단계, 실행 준비 단계, 프로그램 실행 중 어디에서 발생했는지 판단합니다.

선수 지식은 [1.1 Java, JVM, JDK의 관계](./java-jvm-jdk.mdx)입니다. JDK의 도구인 `javac`와 `java`를 구분했다면 시작할 수 있습니다. 패키지·클래스패스·JAR의 상세 사용법은 **1.3**, 클래스 로딩과 실행 엔진의 내부 구조는 **13장 JVM 핵심**에서 다룹니다.

## 핵심 개념

### 컴파일은 실행할 프로그램을 준비하는 단계입니다

편집기에서 저장한 `.java` 파일에는 사람이 작성한 Java 소스 코드가 들어 있습니다. **`javac`는 이 소스를 읽어 JVM에서 사용할 클래스 파일을 만듭니다.** 소스의 문법이나 타입 규칙을 어기면 이 단계에서 오류가 납니다. 컴파일러가 `main`을 실행해 프로그램의 모든 동작을 시험하는 것은 아닙니다. [근거: javac Description][javac], [JLS §5.2][assignment]

예를 들어 아래에서 작성할 `Receipt.java`를 컴파일하면 `Receipt.class`가 생깁니다. 수량과 가격을 계산해 화면에 결과를 보여주는 일은 그다음 실행 단계에서 일어납니다.

### 클래스 파일에는 바이트코드와 부가 정보가 들어 있습니다

**바이트코드(bytecode)**는 JVM 명령을 바이트 단위로 표현한 코드입니다. `.class` 파일에는 메서드의 바이트코드뿐 아니라 클래스 이름, 메서드 정보, 파일 형식의 버전 같은 정보도 들어 있습니다. 따라서 클래스 파일 전체를 “명령만 나열한 파일”로 생각하면 빠지는 부분이 있습니다. [근거: JVMS §1.2][jvm-intro], [§4.1][class-file], [§4.7.3][code]

이 파일은 텍스트 편집기로 읽기 위한 Java 소스도, 특정 CPU가 곧바로 실행하는 기계어 파일도 아닙니다. JVM 구현체가 클래스 파일을 읽고 실행 규칙을 구현합니다. JVM이 인터프리터나 기계어 변환을 어떻게 활용하는지는 구현의 영역입니다. [근거: JVMS §1.2][jvm-intro]

### 실행 도구는 JVM에서 시작할 클래스를 지정합니다

이 글의 `java -cp . Receipt`에서 `Receipt`는 **실행을 시작할 클래스 이름**입니다. `java` 실행 도구는 JVM을 시작하고 지정된 클래스의 `main` 메서드가 호출되도록 합니다. `-cp .`은 이 예제의 클래스 파일을 현재 디렉터리에서 찾도록 지정합니다. [근거: java Description·Standard Options][java]

## 예제

### 1. 소스를 저장하고 컴파일하기

JDK의 `javac`, `java`, `javap`를 터미널에서 사용할 수 있어야 합니다. `javac --version`과 `java --version`으로 컴파일 도구와 실행 환경이 이 문서의 기준 버전에 맞는지 확인하세요. 명령 자체를 찾을 수 없다면 먼저 JDK 설치와 실행 경로 설정을 확인해야 합니다.

빈 실습 디렉터리를 만들고 아래 내용을 **`Receipt.java`**로 저장합니다. `public class Receipt`의 이름과 파일 이름의 대소문자를 맞춥니다.

```java title="Receipt.java"
public class Receipt {
    public static void main(String[] args) {
        int count = 3;
        int unitPrice = 400;
        int total = count * unitPrice;
        System.out.println(total);
    }
}
```

이 프로그램은 400원짜리 물건 3개의 합계를 출력합니다. `main`의 선언은 실행 시작점의 형태로 받아들이고, 수량·가격·곱셈·출력의 순서에 집중하면 됩니다. `println(int)`는 정수를 출력하고 줄을 끝냅니다. [근거: java Description][java], [PrintStream.println(int)][println]

터미널에서 파일을 저장한 디렉터리로 이동한 뒤 컴파일합니다.

```bash title="소스 파일 컴파일"
javac Receipt.java
```

이 예제는 성공하면 별도의 메시지 없이 끝나며, 같은 디렉터리에 `Receipt.class`가 생깁니다. **아직 `1200`은 출력되지 않습니다.** `javac`에 출력 디렉터리 옵션을 주지 않았으므로 소스 옆에 클래스 파일이 만들어집니다. [근거: javac Description·-d 옵션][javac]

### 2. 만들어진 클래스를 실행하기

같은 디렉터리에서 다음 명령을 실행합니다.

```bash title="클래스 실행"
java -cp . Receipt
```

```text title="실행 결과"
1200
```

여기에는 `.java`나 `.class` 확장자를 붙이지 않습니다. 명령의 마지막 자리는 실행할 **클래스 이름**을 지정하는 자리이기 때문입니다. 파일 이름을 입력했던 `javac Receipt.java`와 비교해 보세요. [근거: java Synopsis][java]

### 3. 바이트코드를 짧게 살펴보기

클래스 파일을 사람이 확인할 수 있게 풀어 보여주는 JDK 도구가 `javap`입니다. `-c` 옵션으로 메서드의 JVM 명령을 확인합니다. [근거: javap Description·Options][javap]

```bash title="생성된 클래스 파일 살펴보기"
javap -c -classpath . Receipt
```

직접 컴파일한 예제의 출력에서 `main`의 곱셈 부분만 발췌하면 다음과 같습니다. 전체 출력에는 생성자와 다른 명령도 포함됩니다.

```text title="javap 출력 중 곱셈과 저장 부분"
6: iload_1
7: iload_2
8: imul
9: istore_3
```

이 예제에서 앞의 두 명령은 수량과 가격을 계산에 사용할 수 있도록 가져오고, `imul`은 두 `int` 값을 곱합니다. `istore_3`는 결과를 지역 변수의 저장 공간에 넣습니다. 왼쪽 숫자는 소스 코드의 줄 번호가 아니라 메서드 바이트코드 안의 바이트 위치입니다. 명령과 위치는 컴파일러가 만든 결과를 읽은 것이며, 모든 컴파일러가 같은 명령열을 만들어야 한다는 뜻은 아닙니다. [근거: JVMS의 iload 계열·imul·istore 계열][instructions], [Code 속성][code]

지금은 **Java로 쓴 계산이 JVM 명령으로 표현되어 클래스 파일에 들어 있다**는 연결을 확인하면 충분합니다. 각 명령과 JVM의 스택 구조를 외울 필요는 없습니다.

### 4. 소스만 수정하면 실행 결과가 바뀔까?

`Receipt.java`의 `int count = 3;`을 `int count = 4;`로 바꾸고 저장합니다. 이어서 아래 순서대로 확인하세요.

<div className={styles.comparison} role="region" aria-label="소스 수정과 재컴파일 비교" tabIndex={0}>

| 수행한 작업 | 클래스 파일의 상태 | 실행 출력 |
|---|---|---|
| 소스만 수정·저장 | 수량이 3일 때 만든 파일이 남아 있음 | `1200` |
| `javac Receipt.java`를 다시 실행해 성공 | 수량이 4인 소스를 반영한 파일로 갱신 | `1600` |

</div>

각 행의 작업을 마친 뒤 `java -cp . Receipt`로 실행한 결과를 위에서 아래로 비교합니다. 좁은 화면에서는 표를 좌우로 움직여 읽을 수 있습니다. IDE의 자동 컴파일을 사용하지 않는 상황을 가정합니다. **소스의 수정 내용은 다시 컴파일한 뒤 클래스 파일에 반영됩니다.** 도구의 입출력 계약을 바탕으로 직접 구성하고 실행해 확인한 비교입니다. [근거: javac][javac], [java][java]

## 오류가 발생한 단계 구분하기

프로그램이 동작하지 않을 때는 **어떤 명령을 실행했고, 어디까지 성공했는지**부터 확인합니다. 다음 오류들은 일부러 만들어 보는 학습 예제입니다. 진단 메시지의 언어와 세부 문구는 환경에 따라 달라질 수 있습니다.

### 컴파일 오류: 소스의 타입이 맞지 않습니다

`Receipt.java`에서 수량을 선언하는 줄을 아래처럼 바꿉니다.

```java title="컴파일 오류를 만들기 위한 한 줄 변경"
int count = "3";
```

`javac Receipt.java`를 실행하면 문자열을 `int` 변수에 넣을 수 없다는 컴파일 오류가 납니다. 확인한 진단의 핵심 문구는 `incompatible types: String cannot be converted to int`입니다. 숫자 `3`과 따옴표로 감싼 문자열 `"3"`은 타입이 다릅니다. [근거: JLS §5.2 Assignment Contexts][assignment]

**이때 다음 실행 단계로 넘어가지 말고 오류를 고칩니다.** 이 실험처럼 이전에 컴파일한 `Receipt.class`가 있으면, 컴파일이 실패해도 예전 파일이 남아 있을 수 있습니다. 따라서 클래스 파일의 존재만으로 이번 컴파일이 성공했다고 판단하면 안 됩니다. 이 단일 파일 실험에서는 이전 결과인 `1600`을 출력하는 파일이 남습니다.

수량 선언을 `int count = 3;`으로 되돌린 뒤 다시 컴파일하면 정상 상태로 돌아옵니다.

### 실행 준비 오류: 시작할 클래스를 찾지 못합니다

정상적으로 컴파일한 뒤, 클래스 이름의 철자를 일부러 바꿔 실행합니다.

```bash title="클래스 이름을 잘못 지정한 실행"
java -cp . Recepit
```

실제 이름은 `Receipt`이므로 `Recepit`을 찾을 수 없습니다. 이 예제에서는 기본 클래스를 찾거나 로드할 수 없다는 안내와 `ClassNotFoundException: Recepit`이 나옵니다. `main` 안의 계산은 시작되지 않았습니다. 명령을 `java -cp . Receipt`로 고쳐 실행하세요. [근거: java의 클래스 지정·클래스패스 옵션][java]

같은 이름이라도 다른 디렉터리에서 `-cp .`을 사용하면 파일을 못 찾을 수 있습니다. `.`은 명령을 실행하는 현재 디렉터리입니다. 여기서는 이름과 현재 위치를 확인하는 데 집중하고, 탐색 경로를 구성하는 방법은 1.3에서 배웁니다.

### 실행 중 예외: 컴파일은 됐지만 계산을 마치지 못합니다

다음 파일은 나누어 받을 인원 수를 0으로 설정한 예제입니다.

```java title="Share.java — 실행 중 예외를 확인하는 예제"
public class Share {
    public static void main(String[] args) {
        int people = 0;
        int perPerson = 12 / people;
        System.out.println(perPerson);
    }
}
```

```bash title="컴파일 성공 후 실행 중 예외 확인"
javac Share.java
java -cp . Share
```

`javac`는 성공하지만 실행 중 정수를 0으로 나누는 계산에서 `ArithmeticException`이 발생합니다. `println`까지 도달하지 않으므로 계산 결과 대신 표준 오류에 다음 진단이 나옵니다. [근거: JLS §15.17.2][division]

```text title="예외 진단 예시"
Exception in thread "main" java.lang.ArithmeticException: / by zero
    at Share.main(Share.java:4)
```

`Share.java:4`는 이 예제에서 나눗셈을 수행한 소스 줄을 가리킵니다. `people`을 `3`으로 고치고 다시 컴파일·실행하면 `4`가 출력됩니다. **컴파일 성공은 실행 중 예외가 없거나 계산이 요구사항에 맞는다는 보장이 아닙니다.** 예외를 처리하는 방법은 4장에서 이어서 다룹니다.

단계별로 정리하면 다음과 같습니다.

| 실패한 단계 | 이 글의 재현 사례 | 먼저 확인할 것 |
|---|---|---|
| 컴파일 | 문자열을 `int`에 대입 | 컴파일러가 가리킨 소스와 타입 |
| 실행 준비 | `Recepit`으로 잘못 지정 | 클래스 이름과 탐색 위치 |
| `main` 실행 중 | 정수를 0으로 나눔 | 예외 종류와 소스 위치, 계산에 사용한 값 |

</div>

위에서 아래로 소스 검사, 실행 준비, 실제 연산을 비교합니다. 이 표는 직접 실행한 세 사례를 묶은 것으로 모든 Java 오류의 분류표는 아닙니다. 일상적인 “오류”라는 표현과 Java 타입 이름인 `Error`, `Exception`의 구분도 이후 예외 문서에서 다룹니다.

## 주의할 점

### 소스 파일 실행 모드도 내부에서 컴파일합니다

JDK에서는 `java Receipt.java`처럼 소스 파일을 지정하는 실행 모드도 제공합니다. 이 경우 소스를 메모리로 컴파일한 다음 실행하며, 실습 디렉터리에 컴파일 결과를 `.class` 파일로 남기지 않습니다. 컴파일 단계가 사라진 것이 아니라 한 번의 명령으로 컴파일과 실행을 요청한 것입니다. [근거: java의 Source-File Mode][source-mode]

이 글의 파일 변화 실험은 `javac Receipt.java`와 `java -cp . Receipt`를 따로 실행하는 방식입니다. 두 방식을 섞으면 “언제 소스 수정이 반영되는가”를 관찰하기 어려워집니다.

### 클래스 파일에도 지원되는 버전이 있습니다

클래스 파일에는 버전 정보가 있고, JVM이 그 형식을 지원해야 읽을 수 있습니다. 더 최신 환경에서 만든 클래스 파일을 오래된 실행 환경에서 실행할 수 있다고 가정하면 안 됩니다. 지원하지 않는 클래스 파일 버전은 `UnsupportedClassVersionError`의 원인이 됩니다. 이 오류를 만나면 `javac --version`과 `java --version`부터 비교합니다. [근거: JVMS §4.1][class-file], [UnsupportedClassVersionError API][class-version-error]

### 컴파일러와 JVM 내부의 컴파일을 구분합니다

이 글의 **소스 컴파일**은 `javac`가 Java 소스를 클래스 파일로 바꾸는 작업입니다. JVM 구현체가 실행 과정에서 코드를 기계어로 바꾸는 작업은 별도의 층위입니다. “JVM에 JIT 컴파일러가 있다”는 설명을 `javac`가 소스를 준비하는 단계와 합쳐 이해하지 마세요. 인터프리터·JIT의 상세 동작과 최적화는 13장에서 다룹니다. [근거: JVMS §1.2][jvm-intro]

## 다른 기술과 연결되는 부분

- **1.3 패키지, 클래스패스와 JAR**: 이번 예제의 클래스 이름과 `-cp .`을 여러 파일과 라이브러리를 찾는 방법으로 확장합니다.
- **1.4 빌드 도구 입문**: 직접 실행한 컴파일·실행 작업을 빌드 도구가 어떻게 묶어 관리하는지 배웁니다.
- **4장 예외와 자원 관리**: 실행 중 발생한 예외를 해석하고 처리하는 방법으로 이어집니다.
- **13장 JVM 핵심**: 실행 준비와 바이트코드 실행을 클래스 로딩·메모리·실행 엔진의 관점으로 살펴봅니다.

각 항목의 범위와 작성 상태는 [Java 로드맵](../../roadmap.mdx#1-java-플랫폼과-실행-구조)에서 확인할 수 있습니다.

## 정리

- `javac Receipt.java`는 소스를 검사하고 클래스 파일을 만듭니다. `java -cp . Receipt`는 준비된 클래스를 JVM에서 실행합니다.
- 클래스 파일에는 JVM 명령인 바이트코드와 부가 정보가 담깁니다. 소스만 저장하면 기존 클래스 파일은 그대로입니다.
- 컴파일 성공, 실행 준비 성공, 프로그램의 정상 동작은 각각 확인해야 합니다. 실패한 명령과 진단 위치를 먼저 읽으면 원인을 좁힐 수 있습니다.

이제 소스를 수정한 뒤 어떤 명령이 필요한지, 오류가 났을 때 소스·실행 명령·실제 연산 중 어디를 먼저 살필지 설명할 수 있으면 됩니다.
