# 조사하고 초안 작성하기

로드맵의 한 주제를 조사하고, 사용자가 꼼꼼히 읽으며 공부하고 다듬을 수 있는 본문까지 작성한다. 자료 목록이나 빈 템플릿만 전달하지 않는다. 초안 작성은 사용자의 검토나 배포 승인을 대신하지 않는다.

아래 파일 경로는 저장소 루트 기준이다.

## 기준 읽기

- `AGENTS.md`, `docs/roadmap.mdx`, `templates/README.md`와 해당 템플릿을 읽는다. 기존 기억보다 현재 파일의 규칙을 우선한다.
- Java는 `templates/study-note.mdx`, Spring Framework·Spring Boot는 `templates/translation.mdx`를 사용한다.
- 영역과 번호로 정확히 한 항목을 식별한다. `1-1`은 해당 영역의 `1.1`로 해석할 수 있으나 여러 영역에 같은 번호가 있고 대화로도 구별할 수 없으면 질문한다.
- 로드맵의 포함·제외 범위, 선수 지식, 기준 버전, 앞뒤 주제를 확인한다. 조사 과정에서 전체 목차나 다른 주제를 임의로 바꾸지 않는다.

## 문서 브랜치 준비 또는 이어 쓰기

1. 현재 브랜치, `git status --short`, 대상 문서와 기존 diff를 확인한다.
2. 이미 해당 문서의 브랜치와 초안이 있으면 이어서 작업한다. 사용자 수정은 보존하고 템플릿으로 덮어쓰거나 브랜치를 중복 생성하지 않는다. 같은 파일에서 사용자 의도와 충돌하는 큰 변경이 필요하면 먼저 확인한다.
3. 새 문서라면 깨끗한 작업 트리에서 아래 순서로 기준을 갱신한다.

   ```bash
   git switch main
   git fetch origin
   git merge --ff-only origin/main
   ```

   브랜치 전환이나 동기화에 방해되는 변경, 로컬 `main`만의 커밋, 분기된 이력이 있으면 멈추고 설명한다. stash, reset, rebase로 강제 정리하지 않는다.
4. 브랜치와 문서 경로를 알린다. 브랜치는 `docs/<area>/<roadmap-number>-<slug>`이며 `<area>`는 `java`, `spring`, `boot`다. 예: `docs/java/1.1-java-jvm-jdk`. 로컬·원격에 같은 이름이 있는지 확인하고, 있으면 내용을 확인해 재사용 여부를 판단한다.
5. 새 브랜치를 생성하고 현재 템플릿으로 MDX를 초기화한다. 문서 경로는 기존 디렉터리 방식과 소문자 kebab-case를 따른다. `main`에서는 본문을 작성하지 않는다.

현재 브랜치에서 안전하게 계속할 수 있는 무관한 dirty 파일은 그대로 두고 수정하지 않는다. 새 작업으로 전환할 수 없는 경우 필요한 정리 선택을 사용자에게 요청한다.

## 실제 출처 조사

- 로드맵에 연결된 공식 자료부터 실제 페이지·절을 읽는다. 검색 결과 요약이나 모델 기억만으로 원문을 확인했다고 하지 않는다.
- Java의 사실·API 계약·버전 차이는 JLS, JVMS, JDK API, OpenJDK, dev.java 등 1차 자료로 확인한다. 공신력 있는 기술 블로그는 이해를 돕는 보조 자료로 쓰고 공식 근거와 구별한다.
- Java는 여러 자료에서 확인한 사실을 바탕으로 설명 순서·문장·예제를 독립적으로 구성한다. 여러 문단을 번역해 이어 붙이거나 Oracle 문서 전체의 번역·재배포가 허용된 것으로 간주하지 않는다.
- Spring Framework·Spring Boot는 선별한 공식 원문의 범위와 제목 구조를 따라 번역한다. 번역 대상으로 사용한 경로·절과 태그 또는 커밋 SHA를 기록한다. 갱신되는 웹 링크만으로 패치 버전을 고정했다고 하지 않는다.
- 기준 버전은 로드맵에서 가져온다. 최신 버전의 기능이나 Preview 기능을 해당 기준의 정식 기능처럼 섞지 않는다.
- 실제 사용한 원문·코드·이미지의 라이선스와 재배포 조건을 확인한다. 저장소의 Apache-2.0 라이선스가 모든 외부 자료에 적용되는 것은 아니다. 필요한 저작권·라이선스·NOTICE·수정 고지를 유지한다. 권리가 불명확한 표현이나 이미지는 복제하지 않으며, 요청한 번역 자체가 불가능하면 근거와 확인 필요 사항을 보고한다.

## 읽을 수 있는 본문 작성

- 템플릿의 메타데이터와 각 절을 실제 내용으로 채운다. 범위 밖 절은 억지로 늘리지 말고 제거하거나 제외 이유를 짧게 설명한다. 빈 항목, TODO, 작성 지시문을 남겨 사용자가 본문을 새로 쓰게 하지 않는다.
- 핵심 개념, 원리, 최소 예제, 주의점, 연결되는 기술과 요약을 주제에 맞게 설명한다. 앞선 문서의 설명은 필요한 만큼 연결하고 이후 주제를 미리 모두 다루지 않는다.
- 핵심 주장과 예제에 실제 읽은 출처를 연결한다. `SourceInfo`와 참고 자료에는 제목·URL·확인한 절 및 버전 식별 정보를 기록한다. 확인한 사실과 해석을 구별한다.
- 번역문에 더한 해설·예제·여러 절을 잇는 설명은 `TranslatorNote`로 구별한다. 원문의 의미를 바꾸는 축약을 완역처럼 표시하지 않는다.
- 예제는 기준 버전에서 컴파일·실행하고 결과를 확인한다. 실행할 수 없는 예제나 의사 코드는 그렇게 표시한다. 로컬 배포판과 세부 버전은 학습 본문에 넣지 않고 검토 보고에 남겨 이후 PR 검증 항목으로 전달한다.

## Java 시각자료

`templates/README.md`의 **Java 시각자료 작성 규칙 전체**를 적용한다. 템플릿 안의 안내 주석은 실제 시각자료와 검증을 대신하지 않는다.

- 의미 있는 시각자료 최소 1개를 본문의 적절한 위치에 직접 작성한다. Mermaid·표·이미지의 선택, 설명·대체 텍스트, 출처·권리·단순화 표시는 템플릿 규칙을 따른다.
- Mermaid를 선택하기 전에 `package.json`과 `docusaurus.config.ts`에서 렌더링 지원을 확인한다. 지원이 없다면 필요한 설정과 영향을 설명하고 설정 변경 범위를 확인한다. 렌더링되지 않는 코드 블록을 완성된 그림으로 보고하지 않는다.
- 실제 렌더링에서 본문·예제와의 일치, 잘림, 모바일 가독성, 밝은/어두운 테마를 확인한다. 생략은 템플릿이 허용한 경우에만 구체적인 이유를 MDX 주석과 보고에 남긴다.

## 검증과 인계

- `draft: true`, `SourceInfo`의 `작성 중` 상태를 유지한다. 로드맵을 완료로 바꾸거나 공개 사이드바에 초안 링크를 추가하지 않는다. 진행 상태의 별도 공개도 요청 없이는 하지 않는다.
- `pnpm typecheck`, `pnpm build`, `git diff --check`를 실행한다. 공개 빌드에서 초안이 제외되므로 **빌드 성공만으로 초안 본문 검증이 끝난 것은 아니다.** 개발 미리보기에서 해당 MDX·코드 블록·시각자료·링크를 별도로 확인한다.
- 검증 실패나 미확인 항목은 그대로 밝힌다. 사용자 검토 전인데 `작성 완료` 또는 검토 완료 날짜를 붙이지 않는다.
- 결과에는 영역·번호·제목, 브랜치, 문서의 절대 경로 링크, 주요 출처·작성 방식, 예제·시각자료 검증 결과, 남은 확인 사항을 간결하게 보고한다.
- 사용자가 직접 읽고 수정할 단계임을 알린다. 요청하면 개인 공통 `quiz-me`·`sparring`을 활용할 수 있으나 자동 실행하거나 배포 조건으로 요구하지 않는다.

## 경계

`git add`, commit, push, PR 생성·변경, 병합, 배포는 하지 않는다. 사용자가 읽고 다듬은 뒤 `Java 1.1 배포해줘` 또는 `$publish-doc`을 요청하면 배포 단계로 넘어간다.
